# AI 응답 회수: 서버가 답장을 끝까지 책임진다

> 동작(상태 기계, 실패 처리, 스케줄러 설정값)의 현재 상태는 [`architecture.md`](../architecture.md) §4.2·§4.3·§4.7·§5가 갖는다.
> 이 문서는 **왜 이렇게 했는지**와 **이번에 하지 않은 것**을 남긴다.

## 목표

사용자가 재시도하지 않아도 서버가 답장을 끝까지 책임진다. 지연과 실패는 앱이 봉봉이 캐릭터의 말로 풀어낸다.

## 문제 상황

1. **한 번 실패하면 끝이었다.** LLM 호출이 `@Retryable` 1회 재시도까지 실패하면 곧바로 `FAILED`가 됐고,
   되살리려면 사용자가 재촉 버튼을 눌러야 했다. 일시적인 OpenAI 장애도 사용자 몫의 재시도로 넘어갔다.
2. **`PENDING` 고착을 회수할 주체가 없었다.** 큐 포화, 큐가 많이 찬 상태의 종료, OOM·강제 종료, 실패 기록
   자체의 실패([`async-task-loss-on-shutdown.md`](async-task-loss-on-shutdown.md) "해결되지 않는 것")로 남은
   `PENDING`은 사용자의 재요청 말고는 되살릴 방법이 없었다.

## 결정

| # | 변경 | 이유 |
|---|---|---|
| 1 | `ai_response.attempt_count` 추가(Flyway V5), `(ai_response_status_type, updated_at)` 인덱스 | 상태 값을 늘리지 않고 "몇 번째 실패인지"를 센다. 인덱스는 회수 대상 조회용 |
| 2 | 실행 시작 시 `attempt_count` 증가, 실패해도 상한 전이면 `PENDING` 유지 | 실패한 실행도 고착된 `PENDING`과 같은 경로(회수)로 다시 실행하면 처리 경로가 하나로 모인다. 시작 시점에 세는 이유는 아래 |
| 3 | 1시간 주기 회수 스케줄러, 조건부 UPDATE로 선점 후 이벤트 재발행 | 스케줄러는 이벤트만 발행하고 LLM 호출은 기존 Async 워커가 한다. 단일 스케줄러 스레드를 붙잡지 않는다 |
| 4 | 실행 3회(최초 1번 + 회수 2번)를 다 쓰면 `FAILED` + Discord | 일기 1건당 LLM 호출 상한을 6번(3회 × `@Retryable` 2번)으로 묶는다 |
| 5 | 재요청 API 멱등화: `FAILED`일 때만 재실행, 나머지는 202 no-op | 새 앱은 재촉 버튼이 없다. 구버전 앱의 버튼은 `FAILED`에서만 의미가 있다 |
| 6 | `awaitTerminationSeconds` 30 → 50, `stop_grace_period` 40s → 60s | OpenAI 전환으로 read 타임아웃이 20초가 되면서 최악 처리 시간이 약 47초로 늘었다 |

### 실행 횟수는 실패가 아니라 시작 시점에 센다

처음 구현은 실패 경로(`@Recover`·`catch`)에서 횟수를 올렸다. 그러면 실행이 실패 기록까지 가지 못하고 끝날 때
(LLM 호출 중 프로세스 종료, 실패 기록 자체의 DB 오류) 횟수가 0에 머물러, 그 일기가 매시간 회수되며 LLM을
끝없이 호출할 수 있었다. 상한이 "실패 기록이 성공했을 때만" 지켜지는 구조였다.

그래서 리스너가 `AiResponseCaller`를 부르기 직전(`startAttempt`)에 센다. `call()` 안에서 세지 않는 것은
`@Retryable`이 `call()`을 다시 불러 중복으로 세기 때문이다. 상한을 다 쓴 행이 회수되면 LLM 없이 `FAILED`로
확정하고 알린다. 큐 포화로 시작조차 못 한 작업은 `startAttempt`를 거치지 않으므로 횟수를 쓰지 않는다.

### AI 응답 이벤트는 한 곳에서만 만든다

회수 경로가 생기면서 `DiaryAiResponseRequestedEvent`를 조립하는 곳이 세 군데(작성·재요청·회수)가 됐다.
필드를 추가할 때 한 경로만 빠뜨리면 재시도할 때만 프롬프트가 달라지는데 컴파일·테스트로 걸리지 않으므로,
`DiaryAiResponseRequestedEvent.from(diary, user)` 하나로 모았다.

### `stale-after` = 10분

회수 대상은 "`updated_at`이 `stale-after` 이상 지난 `PENDING`"이다. 이 여유가 없으면 큐에서 기다리거나 LLM 호출이
진행 중인 행까지 집어 가 같은 일기에 LLM을 두 번 호출한다. 최악 처리 시간(약 47초)에 큐 대기를 넉넉히 더해
10분으로 잡았다. 실패할 때도 `updated_at`이 갱신되므로, 1시간 주기와 합치면 재시도는 **실패 후 10~70분 사이**에 일어난다.

### 수동 재요청은 실행 1회만 허용한다

`FAILED`는 이미 실행 3회를 다 쓴 상태다. 구버전 앱에서 버튼을 눌렀을 때 횟수를 0으로 초기화하면 회수 사이클 전체(LLM
최대 6번, 최대 약 2시간 대기)가 다시 돌고, 사용자는 버튼을 누른 뒤 오래 기다리게 된다. 그래서 횟수를 **상한 바로
아래(상한 − 1)로** 맞춘다. 지금처럼 실행 1회로 끝나고, 실패하면 곧바로 `FAILED`가 되어 사용자가 바로 알 수 있다.
(횟수를 그대로 두면 시작 시점 판정에서 상한 소진으로 막혀 한 번도 실행되지 않는다.)

받아들인 비용:
- "일기 1건당 최대 6번"은 수동 재요청을 뺀 숫자다. 버튼을 누를 때마다 LLM 호출이 최대 2번씩 늘어난다(지금과 같다).
- 수동 재요청이 실패할 때마다 Discord 알림이 다시 간다.

## 앱 쪽 변경 (다음 앱 배포, 디자이너 요청)

| 상황 | 문구 | 버튼 |
|---|---|---|
| 10초 안에 답장 없음 | 봉봉이가 잠깐 자리를 비웠어요.. | 재촉 버튼 제거 |
| 최종 실패 (`FAILED`) | 편지가 봉봉이에게 닿지 못했어요.. | 없음 (여기서 끝) |

- 늦게 도착한 답장은 지금처럼 앱으로 돌아오거나 일기를 다시 열 때 보인다.
- 대기 문구에 "답장이 오면 알려드릴게요"는 넣지 않는다. 앱과 서버 모두 푸시 알림(FCM)이 없어 지킬 수 없는 약속이 된다.

## 나중에 볼 것

- **재요청 API 삭제**: 새 앱 버전이 충분히 퍼진 뒤에 한다.
- **폴링 예산 10초**: LLM 응답 시간(3~20초)보다 짧다. 늘릴지는 앱 쪽에서 판단한다.
- **응답 거부(refusal)로 인한 최종 실패**: 민감한 일기일 가능성이 있다. 따로 다룰지 기획 쪽과 논의한다.
- (선택) 운영 로그 `[AI][Complete] elapsed=`로 10초를 넘는 응답 비율을 확인한다.

## 배포 시 주의

- `stop_grace_period`는 **컨테이너 재생성 시점부터** 반영된다. 이번 배포의 종료 단계는 아직 옛 값(40s)으로 동작한다.
- 배포 직후 첫 회수 실행에서, 배포 이전부터 고착돼 있던 `PENDING`(`attempt_count = 0`)도 다시 실행된다.
  이미 `FAILED`인 행은 회수 대상이 아니다.
